# 开发过程与公开仓库说明

## 为什么公开仓库只有一个初始提交

这是一个求职展示项目，公开仓库经过了两轮整理：

1. 先完成统一分析引擎、报告生成和金标准回归；
2. 再将真实设备名、配置和旧脚本移出公开范围，并重建一个干净的 Git 历史。

因此，公开仓库的提交时间不代表工具的完整开发周期。

这样做是为了避免公开内部设备标识，而不是为了伪造或夸大开发过程。

## 工具的真实演进过程

工具的演进起点不是“先设计一个完整框架”，而是从实际工作问题开始：

1. 人工阅读操作日志，确认录像开关、断电和擦写计数的实际写法；
2. 为单台设备编写统计脚本；
3. 新设备接入时复制脚本并修改；
4. 脚本数量增加到 77 个后，开始出现重复代码、路径写死和结果难核对的问题；
5. 汇总并明确跨天、断电关闭、时钟回退和计数回落等业务口径；
6. 将日志读取、规则判断、指标计算和 Excel 输出拆开；
7. 使用配置描述设备差异；
8. 将现有报告作为金标准，对 10 台设备做逐项回归；
9. 补测试、README、规则文档和脱敏截图。

## 哪些证据是公开的

公开仓库包含：

- 当前统一分析引擎；
- 匿名配置模板和匿名示例配置；
- 8 项使用合成或脱敏数据运行的自动化测试；
- 1 项可选真实数据回归测试；
- 业务规则、回归方法和项目截图；
- 对开发过程的文字说明。

## 哪些证据不公开

以下内容因包含内部信息或真实车辆标识，不进入公开仓库：

- 真实操作日志；
- 真实旧报告；
- 77 个带设备名称和内部路径的旧脚本；
- 未脱敏截图和运行输出。

这些材料保存在本机 Git 忽略目录中，仅用于本人复盘和经许可的内部核验。

## 面试时怎么如实说明

建议直接说明：

> 这个 GitHub 仓库是重构完成后的脱敏快照，不是原始开发仓库。早期 77 个脚本涉及内部数据，所以没有公开。公开部分可以验证工具代码、匿名测试、规则文档和回归方法；真实数据上的完整回归结果产生于内部环境。

这比暗示公开 Git 历史就是完整开发过程更可信。
